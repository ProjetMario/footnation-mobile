## iOS local et signatures existantes

- Le Mac utilise **macOS 15.7.9, x86_64**. [Expo SDK 57 demande Xcode 26.4 ou ultérieur](https://docs.expo.dev/versions/v57.0.0/) ; [Apple indique macOS Tahoe 26.2 ou ultérieur pour Xcode 26.4](https://developer.apple.com/xcode/system-requirements/). Installer Xcode sur l’OS actuel ne suffit donc pas : le build iOS local nécessite un OS compatible ou un autre Mac. Aucune mise à jour système n’a été lancée.
- Seuls les Command Line Tools sont sélectionnés (`/Library/Developer/CommandLineTools`). Xcode complet, `simctl` et `devicectl` ne sont pas disponibles. Une compilation iOS locale nécessite donc d’abord Xcode.
- CocoaPods 1.17.0 est disponible ; les pods n’ont pas été installés pour cette préparation.
- Le trousseau contient trois identités de signature valides : deux de développement et une de distribution. Deux profils locaux correspondent à `com.footnation.app` et expirent le 20 août 2027 : le profil de développement contient un appareil, le profil de distribution aucun appareil enregistré. Aucune clé privée ni identité personnelle n’a été affichée.
- Ces éléments existants doivent être examinés avec le compte Apple retenu avant de générer quoi que ce soit. Le profil de distribution observé ne prouve pas qu’une distribution ad hoc vers l’iPhone souhaité est déjà possible.

## Prochaines vérifications nécessaires

1. Confirmer le compte et le projet Expo cibles, puis vérifier leurs environnements de build ; ne pas créer de projet en doublon.
2. Pour Android local : disposer d’espace, compléter NDK/Gradle puis produire et installer un build sur un appareil disponible.
3. Pour iOS local : disposer d’un Mac sous un OS compatible et installer Xcode 26.4 ou ultérieur. Pour une distribution EAS interne : vérifier l’équipe Apple, le profil adapté et l’enregistrement de l’appareil souhaité.
4. Réutiliser la signature de l’application publiée s’il s’agit d’une mise à jour. Les identifiants de package seuls ne garantissent pas la compatibilité de signature.
5. Sur les builds installés, tester les permissions, les notifications, la capture audio/vidéo, les appels et les liens d’authentification. La génération native et les exports JavaScript ne valident pas ces comportements sur appareil.

Le dernier contrôle des projets Capacitor existants relève Android `versionCode 3` / `versionName 1.0.2`, et iOS `CURRENT_PROJECT_VERSION 4` / `MARKETING_VERSION 1.0`. Ce sont les valeurs du dépôt, pas celles vérifiées dans les consoles. La configuration Expo `1.0.0` reste une base technique : avant un build destiné à remplacer l’application installée, choisir des versions et numéros supérieurs à ceux réellement distribués. `autoIncrement` du profil production ne suffit pas à découvrir seul les numéros d’une ancienne application Capacitor ; initialiser explicitement l’état de version EAS depuis les consoles retenues. Ne pas désinstaller l’application utilisateur pour contourner un refus de mise à jour.

Références officielles : [Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/), [développement local Expo](https://docs.expo.dev/guides/local-app-development/), [distribution interne EAS](https://docs.expo.dev/build/internal-distribution/), [builds EAS locaux](https://docs.expo.dev/build-reference/local-builds/), [compatibilité Java de Gradle](https://docs.gradle.org/current/userguide/compatibility.html), [AGP 8.12](https://developer.android.com/build/releases/agp-8-12-0-release-notes).

## WebRTC — revue de compatibilité SDK 57 / RN 0.86.3

**Aucune incompatibilité certaine de compilation n’a été identifiée par cette lecture ; la compilation et l’exécution restent non vérifiées.** Aucun package, réglage d’architecture ou avertissement n’a été modifié. L’analyse concerne `react-native-webrtc 124.0.8`, `@config-plugins/react-native-webrtc 15.0.2` et les sources React Native 0.86.3 réellement installées.

La [publication officielle 124.0.8](https://github.com/react-native-webrtc/react-native-webrtc/releases/tag/124.0.8) contient déjà des corrections Android et une correction iOS liée à la nouvelle architecture ; cela ne constitue pas une matrice de validation avec RN 0.86.3. Le suivi du mainteneur décrit un travail de compatibilité dans [la discussion nouvelle architecture](https://github.com/react-native-webrtc/react-native-webrtc/issues/1557). Il ne faut pas appliquer `newArchEnabled=false` comme contournement : [RN 0.82 et suivants ignorent la désactivation de la nouvelle architecture](https://reactnative.dev/blog/2025/10/08/react-native-0.82).

Deux points précis restent conditionnels. Sur Android, le callback optionnel `RTCView.onDimensionsChange` utilise encore `getJSModule(RCTEventEmitter)` ; le React Native installé avertit que ce chemin dépend de l’interop. FootNation n’utilise pas ce callback. Sur iOS, les commandes Picture in Picture du package utilisent encore `RCTUIManager.addUIBlock` ; FootNation n’active pas le PiP ni le partage d’écran. Il ne faut pas ajouter de permissions de capture d’écran ou de capacités d’arrière-plan pour les appels au premier plan actuellement proposés.

Un [signalement RN 0.86 concernant les headers non modulaires avec `use_frameworks!`](https://github.com/react/react-native/issues/57774) fournit un cas reproductible, mais ne démontre pas un échec de FootNation : `ios.useFrameworks` n’est pas activé dans les propriétés locales. Le Podfile peut toutefois l’activer via `USE_FRAMEWORKS`, dont la valeur devra être contrôlée dans l’environnement de build retenu. Aucun drapeau de suppression d’erreur de headers n’a été ajouté. Le vieux conseil de désactivation du desugaring présent dans le README du plugin n’a pas non plus été appliqué sans reproduction du défaut associé.

La validation restante est un build Debug puis Release sur chaque plateforme, suivi du chargement de `WebRTCModule`, de l’affichage des flux locaux/distants dans `RTCView`, des permissions refusées/accordées, de l’audio après un message vocal Expo Audio et de l’arrêt caméra/micro à la fin ou au passage en arrière-plan. Vérifier les artefacts Jitsi effectivement résolus et leurs ABI sur ce build. Les obstacles NDK/espace et Xcode/OS décrits plus haut empêchent ces contrôles ici ; l’export Metro et le typecheck ne les remplacent pas. Le routage Bluetooth Android 12+ n’est pas validé et le plugin ne déclare pas `BLUETOOTH_CONNECT` : un support explicite de casque demanderait aussi sa gestion à l’exécution, pas seulement une ligne de manifest. Aucun support Bluetooth supplémentaire n’est annoncé par ce lot.
