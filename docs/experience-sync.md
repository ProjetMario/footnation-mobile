# Synchronisation du parcours — préparation locale

La migration `supabase/migrations/20260911068000_native_experience_projection.sql` n’est pas déployée. Le client appelle `native_experience_sync_available()` : absence connue de RPC (`PGRST202`/`42883`) conserve l’ancien enregistrement du profil seul avec une indication visible ; une erreur réseau n’est pas interprétée comme un schéma absent. Une tentative déjà préparée en mode synchronisé ne bascule jamais silencieusement vers une écriture directe.

`save_native_experience_history(p_expected jsonb, p_history jsonb)` reçoit les instantanés complets, sans identifiant de propriétaire fourni par le client. L’identité vient de `auth.uid()` ; profil existant non suspendu, verrou de ligne, comparaison JSONB et écriture sont effectués dans la même transaction. Un résultat déjà égal au contenu proposé est renvoyé sans nouvelle écriture ni modification des dates. Une base devenue différente provoque `40001`. La colonne `profiles.updated_at` est facultative : le chargement n’en dépend pas et le mode profil-seul protège son UPDATE par égalité du JSONB complet. Les valeurs SQL NULL et JSON null sont prises en compte. La RPC ne retourne une date que si le schéma en possède une.

Le déclencheur du profil ne projette que les objets portant `native_experience_id`. Cet UUID est créé une seule fois à l’ajout ou à l’édition explicite ; un ancien `club_id` doit être reconfirmé dans le sélecteur avant de recevoir une provenance. Une fiche liée exige une année de début à quatre chiffres ; aucune année n’est inventée. La saisie libre reste disponible sans projection. Les dates numériques anciennes reconnues conservent leur valeur ; le libellé de fin `Présent` utilisé par le site reste compatible avec une période en cours, sans réécriture du JSON côté SQL.

Les lignes sont marquées `native_source='profile-history-v1'`. L’unicité historique `(club_id,profile_id,start_year)` et `start_year NOT NULL` sont conservées : une collision avec une ligne manuelle/historique échoue sans modifier le profil ni revendiquer cette ligne. Seules les lignes dont la provenance est certaine peuvent être modifiées ou retirées par synchronisation. Aucune écriture dans les tables d’adhésions, d’équipes, de rôles ou de vérifications n’a lieu. Un déclencheur assure aussi la cohérence lors d’une écriture du profil par un autre client conservant ces marqueurs.

Les politiques restrictives empêchent les clients de fabriquer, modifier ou effacer une projection native en dehors de l’écriture du parcours, même en présence d’une ancienne policy permissive. Les nouvelles projections respectent la visibilité du profil, les blocages dans les deux sens et les suspensions. Le propriétaire conserve l’accès à ses propres données. Les lignes historiques non marquées conservent leurs politiques antérieures. Un administrateur réel actif peut toujours corriger le parcours d’un tiers si la RLS existante autorisait déjà son UPDATE ; cette migration ne lui accorde aucun droit UPDATE supplémentaire. La RPC reste strictement personnelle.

Le client vérifie le compte avec `getUser(token)` et fige le JWT dans un client sans stockage ni rafraîchissement automatique ; les frontières asynchrones vérifient encore l’identité active. Le journal local, enregistré avant la garde réseau TanStack, conserve propriétaire, identifiant de tentative, mode, base et proposition complète. Une reprise attend un appui explicite et relit d’abord le serveur. Le bouton de rechargement lit le résultat actuel puis abandonne seulement la proposition locale ; il n’annule pas une écriture déjà validée. Une autre tentative locale ne peut pas remplacer celle en attente. Une panne/quota du stockage bloque l’envoi.

Après reçu serveur de suppression du compte, `forgetExperienceSaveForAccount(uid)` supprime le seul journal de cet UID et pose un fence persistant ; les anciennes écritures locales ne peuvent pas le recréer. Les FK existantes `profile_id → profiles ON DELETE CASCADE` retirent la projection serveur sans toucher un autre compte. Aucun contenu du parcours ni JWT n’est écrit dans les journaux d’erreurs.

## Vérification locale

Les tests `experienceSave.test.ts`, `experienceRepository.test.ts` et `experienceClub.test.ts` couvrent les UUID explicites, les années, le contenu complet immuable, la non-attribution des anciennes entrées, l’idempotence après réponse perdue, les conflits, la garde hors ligne réelle et les changements de compte/JWT, ainsi que la reprise et la purge isolée du journal. Contrôle TypeScript strict ciblé.

`backend/test-experience-projection.mjs` exécute `backend/tests/experience-projection.sql` et `experience-no-timestamp.sql` dans deux PGlite neufs, sans réseau. La seconde fixture part directement d’un schéma sans `profiles.updated_at` et vérifie migration, sauvegarde, reprise et projection. Les 36 tests client ciblés incluent la sérialisation réelle du SDK PostgREST pour les filtres JSONB et NULL. La fixture principale passe aussi sur PostgreSQL16 isolé sans TCP. `backend/test-release-concurrency.py --suite experience` vérifie une course réelle de deux clients : premier commit, second rejeté par `40001`, profil/projection cohérents, puis reprise sans changement de timestamp. Aucun profil réel n’a été modifié.

## Avant activation

Valider le schéma cible : table et contrainte historiques de `20260506_create_club_experience_members.sql`, `experience_history` JSONB, colonnes de suspension/admin, `user_blocks` et fonction de visibilité de `20260908027000_native_profile_visibility.sql`. Aucun timestamp des profils n’est requis. Appliquer la migration uniquement lors d’un déploiement séparément autorisé, puis tester les parcours iOS/Android avec des comptes de recette. Aucun paramètre secret, Edge Function, cron ou abonnement supplémentaire n’est requis.

Les anciennes écritures séparées du site restent en place et peuvent encore produire leurs propres lignes non attribuées ; elles ne sont pas transformées en projections natives. Aucun rapprochement, backfill, nettoyage de doublons historiques ou éditeur de distinctions personnelles n’est ajouté. `is_current` est recalculé lors d’une modification du parcours, comme sur le site, sans tâche annuelle ajoutée. Les instantanés sont limités à 200 entrées et 128 Kio côté SQL ; la tentative complète est limitée à 96 000 caractères pour tenir dans le stockage privé natif. Ce journal dépend des capacités et du quota du stockage de l’appareil/navigateur ; ce n’est pas un coffre supplémentaire sur le Web.
